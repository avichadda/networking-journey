FIELD NOTE 01 · HOMELAB ARCHITECTURE

Building a Small Homelab: Network, Compute, and Services

A practical look at how networking, virtualisation, DNS, remote access, and self-hosted applications fit together—and how to troubleshoot them one layer at a time.

A homelab does not need a large rack or enterprise hardware to teach useful infrastructure skills. A modest machine, a managed network, and a few services are enough to explore how modern systems connect.

This article uses a small homelab as its example: an Omada-based networking environment, a Microsoft Surface Go running Proxmox VE on a node named pve0, and services involving Docker, AdGuard Home, Tailscale, and Home Assistant.

Configuration note

This is an architecture overview based on the components in scope, not a claim that every component is deployed in one fully integrated configuration. Exact IP addresses, VLAN IDs, bridge names, DNS records, container placement, and firewall rules have not been specified here; substitute the values from your actual setup before running commands.

01 — Think in layers

When a service fails, it is tempting to change its configuration immediately. A more reliable approach is to trace the path from the client to the application.

  1. Physical and wireless connectivity: Is the device connected to Ethernet or Wi-Fi?
  2. Network: Does it have a valid address, gateway, and route?
  3. Name resolution: Does the hostname resolve to the expected IP address?
  4. Host and platform: Is the target machine, VM, or container running?
  5. Application: Is the service listening on the expected port and reachable under the intended policy?

This layered method helps isolate a fault instead of changing several variables at once.

02 — Network layer: gateway, switching, and Wi-Fi

The Omada equipment identified for this lab includes an ER605 gateway, a TL-SG2210MP managed PoE+ switch, compatible Omada access points, and an Omada Controller. These components serve different roles:

  • Gateway/router: routes traffic between the local network and other networks, subject to its configuration.
  • Managed switch: connects wired devices and supports features such as VLANs and PoE where configured and supported.
  • Access points: provide wireless access to the network.
  • Controller: provides central management for supported Omada devices.

A managed switch does not automatically mean VLAN segmentation is active. VLANs, SSID-to-VLAN mappings, trunk/access port settings, DHCP scopes, and firewall policies must be configured consistently before devices are isolated as intended.

Basic connectivity checks

On a Linux machine, start with:

ip addr
ip route
ping -c 4 <default-gateway-ip>

These commands show interface addresses, the routing table, and whether the host can reach its configured gateway. Replace the placeholder with the actual gateway address. A successful ping is useful evidence, but a failed ping alone does not prove the whole network is down—ICMP may be filtered.

03 — Compute layer: Proxmox on pve0

The small-form-factor compute host identified for this lab is a Microsoft Surface Go with 8 GB RAM and a 128 GB SSD, running Proxmox VE. The node name is pve0.

This is a useful environment for learning virtualisation, but its resources are finite. Leave room for the host itself, monitor memory pressure, and avoid assigning all available RAM to guests. Storage capacity and endurance also matter when services write logs, databases, or media metadata.

Proxmox can run virtual machines and Linux containers. Docker is a separate container platform; a common design is to run Docker inside a dedicated Linux VM, but the exact placement in this setup should be confirmed before documenting it as fact.

Useful first checks

hostname
free -h
df -h
ip route

Run these on the relevant Linux host to inspect the hostname, memory, mounted filesystems, and routes. For Proxmox-specific configuration changes, consult the documentation for the installed version and back up configuration before editing network settings remotely.

04 — DNS: make services discoverable

As a homelab grows, opening each service by IP address becomes cumbersome. AdGuard Home can provide DNS filtering and, when configured for it, local DNS rewrites. Tailscale also offers MagicDNS for names within a tailnet. These solve related but different naming problems.

  • Local DNS: names intended for clients using the configured local resolver.
  • MagicDNS: names for devices in a Tailscale network, subject to tailnet DNS settings.
  • Application URL: the hostname and port a browser or client uses to reach a service.

A DNS record does not start a service, open a firewall port, or create HTTPS certificates. Name resolution is only one part of access.

Test name resolution

nslookup <service-hostname>
# or, where available:
dig <service-hostname>

Check which resolver answered and whether the returned address is the one you expect. If results differ between devices, compare their DNS settings and any VPN or split-DNS configuration.

05 — Docker: services and ports

Docker makes applications easier to package and manage, but container networking introduces its own boundaries. A container can be running while its application is unhealthy, its port is unpublished, or its hostname is only resolvable from a particular network.

For a Docker host, useful inspection commands include:

docker ps
docker logs --tail=100 <container-name>
docker port <container-name>
docker network ls

These help identify running containers, recent logs, published ports, and Docker networks. Before changing a Compose file, confirm which ports the application listens on inside the container and which ports are published on the host.

Example diagnostic sequence — not a deployment recipe
# 1. Is the container running?
docker ps

# 2. Are there startup or application errors?
docker logs --tail=100 <container-name>

# 3. Is the expected port published?
docker port <container-name>

06 — Remote access with Tailscale

Tailscale can provide private connectivity between authorised devices without requiring every internal service to be exposed directly to the public internet. MagicDNS can make tailnet devices easier to address. Availability still depends on the device being connected, access controls, host firewalls, and the service listening on the target interface and port.

For administration, use least privilege: grant access only to the devices and people that need it, keep software updated, and avoid exposing management dashboards unnecessarily. Do not assume that joining a tailnet automatically makes every service reachable or appropriately secured.

When a remote connection fails, verify tailnet connectivity first, then name resolution, routing and access policy, host firewall rules, and the target service itself.

07 — Home Assistant and network-dependent services

Home Assistant is a useful homelab workload because integrations can depend on discovery, DNS, multicast, or direct local connectivity. Details vary by integration and network layout.

If an integration cannot discover a device, check that both devices are online and that the network permits the discovery method it uses. VLAN boundaries can block broadcast or multicast discovery unless the network is deliberately configured to support it. Do not disable segmentation broadly just to make discovery work; identify the specific traffic required.

08 — A repeatable troubleshooting checklist

01

LinkIs Ethernet or Wi-Fi connected?

02

AddressDoes the client have the expected IP and subnet?

03

GatewayCan it reach its next hop?

04

DNSDoes the hostname resolve to the correct address?

05

PortIs the target port listening and reachable?

06

PolicyCould a firewall, ACL, or tailnet rule block it?

07

LogsWhat do the host and application logs report?

Change one variable at a time and record what changed. That makes it easier to identify the root cause and reverse a change if necessary.

09 — What to document next

The most useful next step is to create an accurate network inventory. Record the actual device roles, hostnames, IP ranges, DNS resolvers, VLANs (if configured), service locations, and the path used for remote access. Avoid publishing public IPs, credentials, recovery keys, private keys, or sensitive topology details.
